GPU Failure Modes & Fleet Remediation

Everything that breaks in a large GPU cluster, how each failure announces itself, and how warm-spare automation turns a 60-minute outage into a 5-minute swap — or less.

MTBF @ 1,024 GPUs≈ 8 hours
MANUAL SWAP60–120 min
WARM POOL SWAP4–5 min
HOT SPARE SWAP~1–2 min
THEORETICAL FLOOR30–60 s
1

The two halves of the problem

HALF ASENSING
Detection — knowing a node is bad

Passive telemetry (DCGM, Xid events, fabric counters) catches hard failures in seconds. Active load tests and fleet-level statistics catch the slow stuff — drift, stragglers, lemon nodes — that never throws an error.

HALF BACTING
Remediation — swapping it out fast

Cordon the bad node, drain its workloads, pull a pre-validated node from a warm spare pool, and let the scheduler carry on. The physical repair happens later, invisibly, in the provider's back office.

The relationship in one sentence: detection decides when to act and remediation decides how fast — and at scale both must be automated, because failures arrive faster than humans can respond.

2

Why this dominates the economics

Meta's analysis of 150M A100 GPU-hours shows failure is not an edge case — it's a scheduled event. MTBF shrinks roughly linearly with cluster size:

8 GPUsMTBF ≈ 47 days. Ad-hoc human response is fine.
1,024 GPUsMTBF ≈ 8 hours. ~3 failures per day, every day.
16,384 GPUsMTBF ≈ 1.8 hours. Humans cannot keep up.
One synchronous jobA single bad GPU stalls every rank — all nodes wait on the slowest.

The lever is goodput: G = (1 − (checkpoint + rollback + queue-wait)) × efficiency. Checkpointing and rollback loss are bounded by physics once optimized. Queue wait — dead time waiting for a replacement node — is the largest controllable term.

The core promise of automated remediation: cutting queue wait from 60 min (manual) to 5 min (warm pool) on a 1,000-GPU cluster with 3 failures/day lifts goodput from ~81% to ~92%. You pay the saving on every failure, forever.
3

The swap — two layers, one trick

The 5-minute number is an orchestration-layer swap: which physical machine backs a cluster slot. The expensive physical loop (diagnose → repair/RMA → burn-in) runs later, off the critical path, refilling the pool.

Failure mode catalog

Three classes, in ascending order of detection difficulty. Hard failures are a speed problem; slow failures are a statistics problem; systemic patterns are a judgment problem.

4.1 — Hard failures · BINARY · DETECT IN SECONDS · AUTO-REPLACE

ModeWhat happenedSignalAction
BUS DROPGPU falls off the PCIe bus entirely.Xid 79 in kernel log; GPU vanishes from nvidia-smi.Replace node.
UNCORR. ECCDouble-bit / uncontained memory error crashes the workload.Xid 48 (DBE), Xid 94/95 (contained/uncontained).Migrate; row-remap commits on next power cycle — often no RMA needed.
GPU HANGGSP firmware crash or engine timeout; GPU unresponsive.Xid 119/120 (GSP RPC), stuck kernels, DCGM timeout.GPU reset first; replace if recurrent.
NVLINK ERRIntra-node GPU interconnect faults.Xid 74; NVLink error counters.Reset/retrain; replace if persistent.
NODE DEADKernel panic, PSU failure, node stops heartbeating.NodeNotReady; BMC/SEL events; no telemetry at all.Replace node.

4.2 — Slow failures (drift) · NO ERROR THROWN · NEEDS TRENDS + ACTIVE TESTS

ModeWhat happenedSignalWhy it's hard
ECC CREEPCorrectable errors clustering on one HBM stack — memory is dying.Correctable-ECC counter trend per GPU; Xid 63/64 remap events.Each single error is "normal." Act on the rate, before the uncorrectable one kills a job.
THERMAL SAGFailing fan / degraded TIM / DC cooling issue → clock throttling.DCGM throttle-reason flags, clock vs. temp trend.GPU still reports "healthy." You're paying for compute you're not getting.
STRAGGLEROne GPU runs 10% slow; every synchronous allreduce waits for it — the whole job runs at its pace.Per-rank step-time distribution. Only visible from inside the workload.No error anywhere. The training framework is the only sensor — the case for a customer→provider report API.
LINK DEGRADEPCIe downtrains ×16→×8; NVLink lanes drop; IB optics flap.Link-width/speed registers; fabric error counters; per-pair bandwidth tests.Bandwidth silently halves; correctness unaffected.
SDCSilent data corruption: a failing ALU computes wrong answers with no error flag. Loss curves quietly diverge.Periodic known-answer tests on idle GPUs; duplicate-compute spot checks.The scariest mode — undetectable by any counter. Only caught by checking the math.

4.3 — Systemic patterns · FLEET-LEVEL · AUTOMATION MUST YIELD TO JUDGMENT

ModeWhat happenedSignalCorrect response
LEMON NODEPasses idle health checks, fails under real load, cycles back into the fleet repeatedly.Per-serial failure lineage across jobs, tenants, and time.Track a rap sheet per serial; 3 strikes ⇒ permanent removal. Meta: large-job failure rate 14% → 4%.
CORRELATEDSwitch, PDU, or bad driver push takes out many nodes at once.Failures clustered in time and topology (same rack / leaf).Circuit breaker: halt auto-replacement, page a human. Naive automation churns the whole spare pool while the real fault persists.
Two-tier gate for destructive actions: Tier 1 stays dumb and deterministic ("N failures / rack / 60 s ⇒ halt") — no LLM in the sub-minute hot path. Tier 2 is the ambiguous middle where an agent earns its keep: ingest DCGM history, switch counters, config pushes, thermal maps, and serial lineage; output "87% confident it's the leaf switch, not 12 bad nodes — escalate to network, don't burn spares." Minutes-scale latency budget tolerates reasoning.

Hands-on mechanics

# Hard failures announce themselves in the kernel log:
sudo dmesg | grep -i xid
#   NVRM: Xid (PCI:0000:1a:00): 79, GPU has fallen off the bus.

# Drift needs counters, not events — DCGM health + ECC trend:
dcgmi health --check -g 0
dcgmi dmon -e 203,204,230,231   # util, clocks, ECC counters over time
Takeaway: Xid = event (hard failure, seconds). DCGM = time series (drift, needs a baseline and a trend). You need both.
kubectl cordon node-07          # scheduler metadata flag: unschedulable. Instant.
kubectl drain node-07 \
  --ignore-daemonsets --delete-emptydir-data \
  --grace-period=30               # evict pods; preStop hooks get 30 s to checkpoint
kubectl uncordon spare-31        # if the spare is pre-joined: THIS is the whole swap
Takeaway: cordon costs milliseconds. If spares are already registered in the cluster (hot, cordoned), replacement collapses to cordon + uncordon — the 30–60 s theoretical floor, bounded only by detection.
# Pod spec — vanilla Kubernetes, nothing provider-specific:
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "/app/flush-checkpoint.sh"]
terminationGracePeriodSeconds: 30
Takeaway: the "grace period to checkpoint" in provider remediation flows is just the standard k8s container lifecycle hook — run this before SIGKILL, wait up to the grace period.
# Open-loop remediation: provider emits the event, YOU sequence the fix.
# Event (webhook → your automation):
{ "event": "node.unhealthy", "node": "node-07",
  "cause": "xid_79_pcie_bus_drop", "serial": "GPU-8f2c…",
  "action_taken": "cordoned" }        # cordon is always unilateral

# Your logic runs (custom checkpoint, notify, validate), then:
POST /v1/remediations  { "node": "node-07", "action": "replace" }
Takeaway: the API must be bidirectional — events out (provider detects), remediation calls in (customer detects, e.g. stragglers only visible inside the workload). Clean line: provider always cordons (non-destructive), never replaces without the call in open-loop mode.

Remediation approaches compared

ApproachNode back in fleetWhat's pre-paidTradeoff
MANUAL60–120 minNothing — page, triage, provision, validate, restart.Only viable below ~100 GPUs; goodput bleeds at scale.
WARM POOL (provider auto)4–5 minBoot, drivers, GPU init, burn-in. Swap cost = tenant plumbing: VM/bare-metal context, VPC + IB pkey attach, cluster join.Provider controls sequencing; fine for most.
HOT SPARE (pre-joined)~1–2 minEverything, incl. cluster membership + fabric partition — spare sits cordoned in your cluster. AWS-style checkpointless: 1 m 45 s incl. job recovery.Spare capacity billed inside your cluster; you own the automation.
THEORETICAL FLOOR30–60 sSwap = cordon + uncordon; detection is the long pole (NodeNotReady ~40 s default, tunable; Xid ≈ seconds).Only for hard failures — drift inherently takes longer to detect than to remediate.
FT FRAMEWORKSN/A — job survivestorchft-style: communicator reforms around the loss, no full restart.Code changes; ecosystem still maturing. Complements, doesn't replace, node swap.
  • PICK PROVIDER-AUTO WHEN you want failures to disappear and your SLA story to be someone else's problem — the sane default.
  • PICK OPEN-LOOP WHEN you run custom checkpoint/validation flows and need to sequence remediation yourself (big-lab profile).
  • PICK HOT SPARES WHEN queue-wait minutes are worth more than the idle-spare cost — very large synchronous jobs.
  • PRODUCT DEFAULT: auto-remediation ON, opt-out to open-loop; everyone gets the event stream regardless.

If you're the one selling the metal — API checklist

  • EVENTS OUTWebhook/stream of every detection: BMC sensors, DCGM, out-of-band health, remediation lifecycle. Sent to all customers, auto-mode or not.
  • REPORTS IN"Node X is bad, swap it" API. Non-optional: stragglers, lemons, and SDC are only visible from inside the customer's workload — their training framework is your best sensor.
  • CORDON RULEReserve the unilateral right to cordon (non-destructive) even in open-loop mode — a flapping IB link harms the shared fabric. Never replace without the customer's call.
  • LINEAGE DBPer-serial rap sheet (GPU, chassis, NIC tracked separately — parts migrate between hosts): failures, triggering job type, remediation tried, recurrence. Cross-tenant, cross-time. Feeds lemon detection and the Tier-2 agent.
  • CIRCUIT BREAKERDeterministic Tier-1 halt on clustered failures; Tier-2 agent for the ambiguous middle with confidence + recommended action.
  • POOL HYGIENESpares sized to failure rate, topologically spread (not one rack), and health-cycled — idle hardware degrades and firmware goes stale.
8

Gotchas

  1. False positives burn real spares. A thermal blip or transient network hiccup that clears on retry must not trigger replacement — act on patterns over time, never single data points.
  2. The "5 minutes" is infrastructure availability, not job resumption. Your training job still restarts from checkpoint, reforms NCCL communicators, reloads the model — often longer than the hardware swap itself. Read SLAs accordingly.
  3. ECC errors usually don't mean RMA. Row remapping replaces the bad HBM row with a spare row on-die; the fix is recorded in the InfoROM and committed on the next full power cycle. RMA only when spare rows run out.
  4. Synthetic health checks fundamentally can't catch lemons. Some hardware only fails under real production load. The workload is the only test that matters — hence per-serial lineage.
  5. The platform generation barely matters on the swap path. B300-class POST (10–15 min) and cold bring-up (20–30 min) never touch the swap; they only set how fast the spare pool refills.
  6. Watch correlated failures before trusting your automation. The lab below lets you rehearse the whole cordon/drain/swap flow — and a cordon storm — with zero GPUs.

Run it yourself

LAB A — cordon, drain, swap on a laptop cluster

~10 min · needs Docker

  1. Install kind and create a 4-node cluster (Kubernetes-in-Docker; each "node" is a container). install docs

    cat <<EOF | kind create cluster --config=-
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes: [{role: control-plane},{role: worker},{role: worker},{role: worker}]
EOF
kubectl get nodes

    EXPECT: 1 control-plane + 3 workers, all Ready.

  2. Deploy a workload and mark one worker "failed."

    kubectl create deployment train --image=nginx --replicas=6
kubectl cordon kind-worker
kubectl drain kind-worker --ignore-daemonsets --grace-period=30

    EXPECT: kind-worker shows SchedulingDisabled; pods reschedule onto the other two workers — this is the exact flow from Section 3, minus the GPUs.

  3. Time the "swap-in": uncordon and watch the scheduler use it again.

    time kubectl uncordon kind-worker
kubectl scale deployment train --replicas=12 && kubectl get pods -o wide

    EXPECT: uncordon returns in <1 s — the orchestration swap really is metadata. Everything slower in production is tenant plumbing.

LAB B — simulate a 100-node fleet and a correlated failure

~15 min · needs Docker + kwok

  1. Install kwok (Kubernetes WithOut Kubelet — simulates thousands of fake nodes cheaply). kwok docs Run it inside the LAB A cluster, then create 100 fake nodes with a rack label:

    kwokctl create cluster --name sim
kwokctl --name sim scale node --replicas 100
# label 10 fake nodes per "rack":
i=0; for n in $(kubectl --context kwok-sim get nodes -o name); do
  kubectl --context kwok-sim label $n rack=rack-$((i/10)); i=$((i+1))
done

    EXPECT: kubectl get nodes shows 100 fake Ready nodes, 10 per "rack".

  2. Simulate a correlated failure: cordon every node in one rack at once.

    kubectl --context kwok-sim cordon -l rack=rack-3

    EXPECT: 10 nodes go SchedulingDisabled simultaneously — the exact signature (clustered in time + topology) your Tier-1 circuit breaker must catch before auto-replacement drains the spare pool.

  3. Write the circuit breaker as a 10-line script: count cordoned nodes per rack label per minute; if > 3, print HALT AUTOMATION — ESCALATE instead of "replacing."

    EXPECT: single-node cordons pass through; the rack-wide event trips the breaker. You've built Section 4.3.

LAB C — graduation: real GPU telemetry

optional · needs an NVIDIA GPU

  1. Run dcgm-exporter and watch the counters that drive drift detection. github.com/NVIDIA/dcgm-exporter

    docker run -d --gpus all --cap-add SYS_ADMIN -p 9400:9400 \
  nvcr.io/nvidia/k8s/dcgm-exporter:latest
curl -s localhost:9400/metrics | grep -E 'ECC|THERMAL|CLOCK'

    EXPECT: Prometheus-format ECC counters, throttle reasons, and clocks — the raw feed behind every table in Section 4. Trend these, don't threshold them.

Glossary

Cordon
Kubernetes scheduler flag marking a node unschedulable — nothing new lands on it. Pure control-plane metadata, instant, non-destructive. k8s docs
Drain
Evicting a cordoned node's running pods, honoring grace periods and preStop hooks so workloads can checkpoint before termination.
DCGM
NVIDIA Data Center GPU Manager — the telemetry layer (temps, clocks, ECC counters, throttle reasons, health checks) every fleet monitor is built on. nvidia.com/dcgm
Xid
NVIDIA driver error codes written to the kernel log when a GPU fault occurs — e.g. 79 = fell off the bus, 48 = double-bit ECC, 119/120 = GSP firmware faults. Xid reference
Row remapping
HBM's self-repair: a failing memory row is replaced by a spare hardware row on the die. Scheduled in software immediately; committed permanently on the next full power cycle.
InfoROM
Persistent non-volatile storage on the GPU board recording remapped rows and retired pages, so protections survive reboots and reinstalls.
SEL
System Event Log — the BMC's own hardware log (ECC, thermal trips, PSU faults), readable even when the host is dead. The BMC is the tiny always-on management computer inside every server.
MTBF
Mean time between failures. Shrinks roughly linearly with component count: what's 47 days at 8 GPUs is ~8 hours at 1,024.
Goodput
The fraction of paid compute time spent doing useful work — what remains after checkpoint overhead, rollback loss, and queue wait.
Warm / hot spare
Warm: powered, booted, burn-in-validated, waiting in the provider's pool. Hot: additionally pre-joined to your cluster and fabric partition, sitting cordoned — swap-in is just uncordon.
Burn-in
Stress, memory, and fabric testing before a node enters service. Paying validation up-front is what makes zero-validation swaps possible later.
Straggler
A GPU running slower than its peers with no error. In synchronous training every collective waits for the slowest rank, so one straggler sets the pace of the whole job.
Allreduce
The collective operation (via NCCL) that synchronizes gradients across all GPUs each training step — the reason one slow or dead GPU stalls everyone.
SDC — silent data corruption
Hardware computes a wrong result with no error flagged. Detectable only by re-checking the math: known-answer tests, duplicate computation.
Lemon node
Hardware that passes idle health checks but fails repeatedly under real load, cycling through the fleet. Cured only by per-serial failure lineage and permanent exclusion.
RMA
Return Merchandise Authorization — sending failed hardware back to the vendor for repair or replacement. The slow, terminal branch of the physical loop.
Open-loop remediation
Provider detects and emits events; the customer's automation sequences the response and calls the remediation API to trigger replacement. The opt-out from full auto.
IB pkey / partition
InfiniBand's tenant-isolation mechanism — a partition key scoping which nodes can talk on the fabric. Attaching a spare to the right partition is part of the "4 minutes."
