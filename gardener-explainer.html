What it is

Gardener is open-source software, started inside SAP and released under Apache-2.0, that runs Kubernetes clusters as a service — the thing EKS, GKE and AKS sell, except you run it yourself, on any infrastructure, and every cluster it hands out is identical. It has two halves, and people usually only know one of them.

The interfacecore.gardener.cloud

A Kubernetes API that hands out Kubernetes clusters.

You don't call a vendor REST API or click a console. You kubectl apply a Shoot resource into a cluster, and a Kubernetes cluster appears. Gardener's API is served by an aggregated API server — a standard Kubernetes extension point — so Shoot is as native an object as Pod.

That means every tool that speaks Kubernetes already speaks Gardener: kubectl, client-go, Terraform's Kubernetes provider, Argo CD, your own controllers. There is no SDK to learn.

The mechanism"Kubeception"

Your cluster's control plane is a Deployment in someone else's cluster.

A normal Kubernetes cluster runs its control plane — etcd, kube-apiserver, scheduler, controller-manager — on dedicated master machines. Gardener instead schedules them as ordinary pods in a namespace of another Kubernetes cluster, which it calls a seed.

The cluster you get, the shoot, is then only its worker nodes. Its control plane lives somewhere you never see — and because it's just pods, it costs pods, scales like pods, and updates by rolling update.

The relationship in one sentence: the Shoot API is what you touch; kubeception is what makes it cheap enough to hand out thousands of times.

A naming note before anything else. Gardener's vocabulary is a garden metaphor and it is load-bearing, so it's worth fixing now: a garden cluster runs Gardener itself; a seed cluster hosts other clusters' control planes; a shoot cluster is the one an end user gets. Clusters are grouped into Projects, and one landscape is one garden plus its seeds plus everything under them. Everything else in this sheet is built on those words.

The job it solves

One Kubernetes cluster is a solved problem — eksctl, kubeadm, or a console wizard. Gardener exists for the point where that stops working: when clusters become a fleet, and the fleet spans providers you don't control equally.

You need 400 clustersAt three control-plane VMs each, that's 1,200 machines doing nothing but running etcd. As pods, they're a scheduling problem instead of a procurement one.
Four clouds, one platform teamEKS, AKS and GKE differ in versions, add-ons, upgrade cadence and defaults. Gardener's clusters are byte-for-byte the same shape on all of them.
Half the fleet is on-premOpenStack and bare metal get the same Shoot object, the same versions, the same rotation procedures as the hyperscaler clusters.
Dev clusters idle 16 hours a dayHibernation scales the workers and the control plane to zero on a cron, and etcd's contents survive it.
A Kubernetes version is going EOLMark it expired in the catalog with a date; every cluster still on it gets force-upgraded in its own maintenance window. No spreadsheet, no chasing teams.
A whole region has to moveChange one field and a cluster's control plane migrates to a different seed — in a different data centre, or on a different cloud — while its workers keep running.
The core promise: homogeneous clusters. The claim is not "provisions on any cloud" — most tools do that. It is that a cluster on Azure and a cluster in your own OpenStack rack carry the same Kubernetes version, the same CNI, the same DNS, the same credential-rotation procedure, and the same behaviour when you upgrade them. That harmonisation, not the provisioning, is the product.

What Gardener actually gives you per cluster

  • PROVISIONInfrastructure (VPC, subnets, IAM), control plane, worker pools and CNI from a single declarative object.
  • UPGRADEKubernetes and node-OS versions with a classification lifecycle — preview → supported → deprecated → expired — and forced upgrades on expiry.
  • ROTATEMulti-phase rotation of cluster CAs, the ServiceAccount signing key, the etcd encryption key, the SSH keypair and observability credentials.
  • HIBERNATEHibernation scales a whole cluster — workers and control plane — to zero and back, preserving etcd state.
  • SSHOn-demand Bastion hosts for node access, with firewall rules scoped to your address and a hard lifetime cap.
  • HAOptional node-level or zone-level failure tolerance: 3-member etcd and spread control-plane replicas, configured with one field.
  • OBSERVEA per-cluster Prometheus, log aggregation and dashboards, deployed into the seed alongside the control plane.
  • MIGRATEMove a live cluster's control plane between seeds, restoring etcd from backup at the destination.
  • BACKUPContinuous etcd backup to object storage — full snapshots daily, deltas every five minutes.
  • EXTENDAn extension contract that keeps every cloud-specific line of code out of the core, in separately versioned controllers.

Kubeception — the trick, in one picture

Every managed-Kubernetes product has to answer one question: where does the control plane run? EKS and GKE run it on machines you never see and charge you per cluster-hour. kubeadm runs it on machines you buy. Gardener runs it as pods, in a namespace, on another Kubernetes cluster — and that one decision explains almost everything else about the system.

garden — Gardener's own control plane seed — hosts shoots' control planes shoot — the delivered cluster connection Gardener initiates connection the shoot initiates
FIG. 3-1 — Kubeception. A "Kubernetes cluster" delivered by Gardener is one namespace of pods in a seed, plus a set of worker nodes. Nothing else exists.

Why it's a kubelet in disguise

The architecture is a deliberate, almost line-by-line re-implementation of Kubernetes itself, one level up. Gardener's own docs state the mapping outright, and internalising it is the fastest way to predict how the system behaves:

In KubernetesIn GardenerSame idea
kube-apiservergardener-apiserverThe single declarative front door. Gardener's is an aggregated API server, so it is literally part of the garden cluster's API.
kube-schedulergardener-schedulerFinds a place to run the thing. Instead of "which node fits this pod," it asks "which seed fits this shoot."
kube-controller-managergardener-controller-managerThe bag of reconcile loops for objects nobody else owns — Projects, quotas, extension rollout.
kubeletgardenletOne agent per host, responsible only for what runs on its host. A kubelet owns its node's pods; a gardenlet owns its seed's shoots.
PodShootThe unit of work you declare and the system places.
NodeSeedThe capacity you place work onto. Seeds even have a shoot capacity, and the scheduler filters on it.

The recursion goes one step further than the table suggests. A seed is just a conformant Kubernetes cluster with a gardenlet in it — and the usual way fleets grow seed capacity is to take an existing shoot and promote it, with a ManagedSeed object. The parent gardenlet clones itself into the shoot, and a cluster Gardener created starts hosting other clusters.

The pull model, and why it matters more than it sounds

Note the arrow direction in FIG. 3-1: the gardenlet contacts the garden cluster, never the reverse. Gardener calls this the "reversed control flow," and it is the same reason kubelets poll the API server rather than being pushed to. The consequence is architectural, not cosmetic — a seed can sit inside a customer's private network, behind a firewall with zero inbound rules, and still be fully managed.

The same reversal was later applied one layer down. The original design had the seed dial into the shoot over a VPN, which meant every shoot cluster had to publish a VPN endpoint — Gardener's own proposal put the cost of that endpoint at "roughly €20/month on hyperscalers," multiplied by every cluster in the fleet. Today the vpn-shoot client dials out to vpn-seed-server instead. One direction flip removed a per-cluster load balancer and a firewall-rule conversation with every customer.

One load balancer for a thousand clusters

The same instinct — refuse to buy a per-cluster resource — shows up in how a shoot's API server is reached. The obvious design gives every shoot its own load balancer; Gardener's own proposal listed why that fails at scale: cost, provider quota limits, and provisioning delay on every cluster creation.

Instead a seed runs one Istio ingress gateway behind one network load balancer, shared by every shoot on it. Envoy reads the requested hostname from the unencrypted SNI field of the TLS handshake and forwards the still-encrypted stream to the right namespace's kube-apiserver. Nothing is decrypted in between, so client-certificate authentication still terminates where it should.

There is one place that trick cannot work: clients inside a shoot reach the API server through the kubernetes.default.svc service, and that hostname is byte-identical for every shoot in the world — SNI carries no information. Gardener's answer is apiserver-proxy, a host-network DaemonSet on every node that intercepts traffic to that address and tunnels it out over the same reversed VPN connection. It is a small piece of machinery, and it exists purely because the cheap answer had one hole in it.

The consequence worth remembering: because the control plane is not in the user's cluster, the user can be given full cluster-admin on their shoot without any risk to the control plane — they cannot reach it. Contrast with a self-managed cluster, where cluster-admin and "can destroy etcd" are the same permission.

Talking to it

There is no Gardener CLI you must learn and no proprietary API. Everything below is plain kubectl against the garden cluster. Click through the tabs — each one is a real operation on a real cluster, with the takeaway underneath.

# The entire ask. Apply this to the garden cluster and a cluster appears.
apiVersion: core.gardener.cloud/v1beta1
kind: Shoot
metadata:
  name: prod
  namespace: garden-acme        # the Project's namespace
spec:
  cloudProfile:
    name: aws                  # catalogue of allowed versions/machine types
  region: eu-central-1
  credentialsBindingName: acme-aws   # NOT the credential — a reference to one
  kubernetes:
    version: "1.34.5"
  networking:
    type: calico
    nodes: 10.250.0.0/16
  provider:
    type: aws
    workers:
    - name: default
      machine: {type: m5.large}
      minimum: 3
      maximum: 10            # max > min silently enables cluster-autoscaler
      zones: [eu-central-1a, eu-central-1b, eu-central-1c]
  controlPlane:
    highAvailability:
      failureTolerance: {type: zone}   # 3-member etcd across 3 zones
  maintenance:
    timeWindow: {begin: "220000+0100", end: "230000+0100"}
Takeaway: notice what is absent. No AMI ID, no security-group rules, no etcd sizing, no CA configuration, no kubeadm join tokens. The CloudProfile named here is a catalogue an administrator curates — it decides which Kubernetes versions and machine types this project is even allowed to ask for. And credentialsBindingName points at a credential rather than carrying one; CredentialsBinding replaced the older SecretBinding, which is rejected outright for shoots on Kubernetes 1.34 and newer. It can also point at a WorkloadIdentity instead of a Secret, in which case no static cloud credential exists anywhere at all.

# Meanwhile, in the SHOOT itself:
$ kubectl get pods -n kube-system --context=shoot
# calico-node, coredns, kube-proxy, csi-driver, vpn-shoot …
# and NO apiserver, NO etcd, NO scheduler. There is nothing to find.
Takeaway: a "cluster" is a namespace. etcd-main holds cluster state and etcd-events is split out so high-churn Event objects cannot crowd it — a real production lesson baked into the topology, and the reason only etcd-main is ever backed up. Both are run by etcd-druid rather than by Gardener directly. Everything here is an ordinary Deployment or StatefulSet, which is exactly why upgrading a control plane is a rolling update and why replicas: 1 is acceptable: the seed's own scheduler will restart it. Gardener's own guidance bands seed density from 15 control planes per seed node up to 120+.

# One hour later, that file is a paperweight. Ask again.
Takeaway: the static per-shoot kubeconfig Secret that older Gardener docs and blog posts describe is gone. Access is a short-lived, RBAC-gated request against the shoots/adminkubeconfig subresource, so revoking someone means revoking their RBAC in the garden cluster rather than rotating a cluster CA. A viewerkubeconfig variant issues read-only credentials the same way.
# Scale an entire cluster — workers AND control plane — to zero.
# etcd's contents survive; the machines and pods do not.

spec:
  hibernation:
    enabled: true
    schedules:
    - start: "0 20 * * 1-5"     # 20:00 on weekdays: sleep
      end: "0 7 * * 1-5"        # 07:00 on weekdays: wake
      location: "Europe/Berlin"  # IANA zone, so DST is handled

# Or right now, from the command line:
$ kubectl -n garden-acme patch shoot dev --type=merge \
    -p '{"spec":{"hibernation":{"enabled":true}}}'

$ kubectl -n garden-acme get shoot dev
NAME   STATUS      HIBERNATION   AGE
dev    Hibernated  Hibernated    31d
Takeaway: this is the feature people adopt Gardener for and then get a surprise bill from. Hibernation stops compute. It does not delete persistent volumes, release load-balancer IPs, or free floating IPs — all of which keep billing. And because rotating the etcd encryption key needs a running etcd, automatic rotation is skipped while hibernated; if your maintenance window never overlaps an awake period, Gardener raises an AutomaticCredentialsRotationPossible=False constraint rather than silently skipping forever.
# Rotating a cluster CA without downtime is a two-phase handshake,
# because clients need a window where BOTH CAs are trusted.

$ kubectl -n garden-acme annotate shoot prod \
    gardener.cloud/operation=rotate-ca-start
# → new CA issued alongside the old; EVERY worker node is rolled
#   so kubelets pick up fresh credentials. Phase: Preparing → Prepared.

# ... now you update every out-of-cluster client that pinned the old CA ...

$ kubectl -n garden-acme annotate shoot prod \
    gardener.cloud/operation=rotate-ca-complete
# → old CA dropped. Phase: Completing → Completed.

# The same start/complete shape covers the ServiceAccount signing key.
# Single-shot operations exist for the rest:
  rotate-ssh-keypair
  rotate-etcd-encryption-key
  rotate-observability-credentials
  rotate-credentials-start / rotate-credentials-complete   # all at once
Takeaway: rotation is a first-class, scriptable cluster operation rather than a runbook — that is genuinely rare. But the coverage is uneven, and assuming uniformity will burn you: CAs and the ServiceAccount signing key have no automatic rotation at all; the SSH keypair, etcd encryption key and observability passwords do; the OpenVPN TLS auth key has no rotation mechanism whatsoever, manual or automatic. Your cloud-provider credentials are entirely your own problem — Gardener only reconciles whatever the referenced Secret currently holds.
# Gardener tells you exactly which step it is on, by name.
$ kubectl -n garden-acme get shoot prod -o yaml | yq .status.lastOperation

type: Create
state: Processing
progress: 43
description: "Waiting until shoot infrastructure has been reconciled"

# Creating a shoot is 122 of them. The phases, in order:

  1  Deploying Shoot namespace in Seed
     Initializing secrets management
     Deploying cloud provider account secret
  2  Deploying Shoot infrastructure            # the cloud API does the work
     Waiting until shoot infrastructure has been reconciled
  3  Deploying Kubernetes API server service in the Seed cluster
     Deploying internal domain DNS record
     Deploying external domain DNS record
  4  Deploying main and events etcd
     Waiting until main and event etcd report readiness
  5  Deploying Kubernetes API server
     Waiting until Kubernetes API server rolled out
  6  Deploying gardener-resource-manager          # before what it manages
     Deploying shoot control plane components         # CCM, CSI, via the extension
     Deploying Kubernetes scheduler
     Deploying Kubernetes controller manager
  7  Deploying operating system specific configuration for shoot workers
  8  Deploying shoot network plugin                # calico / cilium
     Deploying CoreDNS system component
     Deploying kube-proxy system component
     Deploying vpn-shoot system component
  9  Deploying machine-controller-manager
     Configuring shoot worker pools                   # VMs boot here
     Waiting until shoot worker nodes have been reconciled
 10  Deploying shoot logging stack in Seed
     Reconciling Shoot Prometheus
Takeaway: the flow is a real abstraction in the codebase, not a metaphor — a directed acyclic graph executed with maximum parallelism, where each task's human-readable name is its graph key. That is why a stuck cluster tells you precisely which step it is stuck on. The two steps that dominate wall-clock time are the ones that leave Kubernetes entirely: waiting on the cloud API to build a VPC, and waiting for VMs to boot and register. Everything else is pod scheduling on a seed that is already running.

How one codebase reaches every cloud

Gardener started with every cloud provider's logic compiled into the core. That stopped scaling, and the fix — proposed as GEP-1, the project's first enhancement proposal — is the reason Gardener supports infrastructures its maintainers have never touched: all provider-specific code lives in separate repositories, on separate release cycles, behind a fixed contract.

The contract is deliberately dull. Gardener writes a custom resource with an opaque providerConfig blob it never parses; an extension controller running in the seed reconciles it against the real cloud API and writes back an equally opaque providerStatus. Gardener waits on status.lastOperation and moves to the next step. That is the whole interface.

FIG. 5-1 — Registration pipeline and the extension contract. Nothing about AWS, Azure or OpenStack exists in Gardener's own repository.

The most quietly clever of the ten is OperatingSystemConfig. Gardener describes a worker node in OS-neutral terms — these files, these systemd units — and an OS extension renders that into Garden Linux's, Flatcar's or Ubuntu's native bootstrap format. On the node itself, gardener-node-agent watches for changes and restarts only the units that actually changed, which is why a config tweak does not mean a node replacement.

The payoff shows up in the provider list. AWS, Azure, GCP, OpenStack and Alicloud are maintained by the project itself; Hetzner Cloud comes from 23 Technologies, and bare-metal support comes from two independent projects — metal-stack and IronCore — that ship their own extensions on their own schedules. Beyond infrastructure there are extensions for the node OS, the CNI, DNS, certificate issuance, image-signature enforcement, registry caching and runtime security. None of them require a core release.

Where the worker nodes actually come from. A Worker extension does not create VMs directly — it emits objects for machine-controller-manager, which deliberately mirrors Kubernetes' own hierarchy: MachineClass (a template), Machine (one VM ≈ a Pod), MachineSet (≈ ReplicaSet), MachineDeployment (≈ Deployment, with maxSurge/maxUnavailable). Change an AMI and the MachineClass name changes, which changes the MachineDeployment's template, which triggers a rolling replacement of nodes — using logic every Kubernetes engineer already understands. This design predates Cluster API and, by Gardener's own account, influenced CAPI's machine model.

Alternatives & comparables

Gardener is not the only way to get a fleet of clusters, and for most organisations it is the wrong one. The honest framing: Gardener is a managed-Kubernetes engine — the thing a cloud provider runs in order to sell Kubernetes. Judge it against that, not against a provisioning tool.

PICK GARDENER WHENYou are offering Kubernetes — internally or commercially — across several clouds plus on-prem, at hundreds-to-thousands of clusters, and identical behaviour everywhere is a requirement rather than a nicety. Also the strongest answer when independence from a US hyperscaler is a regulatory constraint.
PICK CLUSTER API WHENYou want the widest provider ecosystem and the largest community, you can accept that a cluster on Azure and a cluster on vSphere will differ, and you are willing to build the version-lifecycle and rotation layer yourself. The de facto standard everything else here bridges to.
PICK KUBERMATIC KKP WHENYou want Gardener's architecture with a vendor's support contract, a polished UI, and someone to call — and the enterprise licence cost is easier for you than the platform headcount.
PICK VCLUSTER WHENThe ask is cheap tenant separation for dev, CI, or per-team sandboxes. It is enormously cheaper and faster than any option here, and it is not a security boundary — the tenants share one kernel and one host cluster.
PICK EKS / GKE / AKS WHENYou are on one cloud with a handful of clusters. Below roughly the point where per-cluster fees exceed a platform engineer's salary, buying beats building — and it is not close.
PICK RANCHER WHENYou do not need a provisioning engine at all. You need one pane of glass, consistent RBAC and GitOps across clusters that already exist, made by anything. Different problem, much larger community.
PICK CROSSPLANE WHENClusters are one item on a much longer list of cloud resources you want behind one declarative API. Accept that cluster homogeneity and Day-2 lifecycle become Compositions you write and maintain.
PICK HYPERSHIFT OR K0SMOTRON WHENYou want control-planes-as-pods without adopting a whole platform. HyperShift if you are already committed to OpenShift; k0smotron for a lightweight, CNCF-sandbox option that also speaks Cluster API.

Three distinctions people get wrong

  • vs CAPIBoth create clusters, but they harmonise different things. Gardener's own docs put it well: "Cluster API primarily harmonizes how to get to clusters, while Gardener goes a significant step further by also harmonizing the clusters themselves." They are also converging rather than competing — cluster-api-provider-gardener, announced in August 2025, lets standard CAPI manifests drive Gardener Shoots.
  • vs vclusterA vcluster is a virtual control plane whose pods run on the host cluster's nodes and share its kernel. A Gardener shoot is a real cluster with its own nodes, its own kernel, its own CNI and its own cloud infrastructure. Both are "control plane as pods"; only one gives you an isolation boundary.
  • vs CrossplaneCrossplane is a framework for controlling any cloud resource declaratively — including clusters, if you write the Composition. Gardener is an opinionated product for exactly one resource. Crossplane is a strictly larger surface and a strictly smaller opinion.
  • NOT rivalsKarmada and Sveltos manage workload placement across clusters that already exist. They sit above the provisioning question and are frequently run on top of Gardener rather than instead of it.

Where it's actually used

Gardener's adopter list is unusually legible about why each organisation picked it, and the reasons cluster into five recognisable shapes. Every company named below is drawn from that public list; the two projects named — metal-stack and IronCore — are there because they maintain bare-metal support themselves.

Hyperscale internal platform

The origin story and still the largest deployment. SAP runs Gardener to deliver the Kubernetes environment underneath its Business Technology Platform, uniformly across every infrastructure it operates on. The project describes itself as born from "years of managing tens of thousands of clusters."

SAP BTP · the reference workload

Sovereign & regulated cloud

The fastest-growing reason, and the one behind Gardener's governance move. European operators need Kubernetes that is auditable end-to-end and independent of any US hyperscaler. Finanz Informatik Technologie Services runs it for German financial-industry customers; STACKIT offers public and private Kubernetes from its own European data centres.

STACKIT · Finanz Informatik · NeoNephos

Reselling managed Kubernetes

If your business is selling Kubernetes, Gardener is the engine rather than the product. plusserver ships it as "PSKE," Cleura as its Container Orchestration Engine, exigo as "exikube," and OVHcloud offers it on its public cloud — each a differently-branded front end over the same shoot API.

plusserver PSKE · Cleura · exigo · OVHcloud

Hybrid and on-prem parity

The case Gardener is uniquely good at: the same cluster shape on a hyperscaler and in your own racks. T-Systems runs it both internally and for customers; noris network combines OpenStack with Gardener into a fully open-source platform; ScaleUp Technologies runs it inside its own OpenStack clouds.

T-Systems · noris network · ScaleUp · OpenStack

Bare metal and edge

Because infrastructure support is an out-of-tree extension, projects with no hyperscaler involvement can make bare metal a first-class Gardener target. metal-stack and IronCore each ship their own provider extension; 23 Technologies targets industrial and edge use cases.

metal-stack · IronCore · 23 Technologies

Cost control at cluster scale

Two features do most of the work here: control-plane density (Gardener bands seed utilisation from 15 to 120+ control planes per seed node) and hibernation on a schedule for the large fraction of clusters that are only used during working hours.

seed bin-packing · hibernation schedules

Ecosystem — decoding the names

Gardener's vocabulary is dense, metaphor-heavy and occasionally invented for licensing reasons. Here is what each proper noun you will encounter actually is.

Runs in the garden

  • gardener-apiserverAggregated API server: the Shoot/Seed/Project/CloudProfile types.
  • gardener-schedulerChooses which seed will host a new shoot's control plane.
  • gardener-controller-managerProjects, quotas, and pushing extensions out to seeds.
  • gardener-admission-controllerHosts the two webhooks that confine a gardenlet to its own seed: SeedAuthorizer for reads, SeedRestriction for writes.
  • gardener-operatorRuns Gardener itself, via a single Garden resource.
  • Gardener DashboardThe web UI most end users actually touch.

Runs in a seed

  • gardenletOne per seed. Reconciles every shoot on it; dials out to the garden.
  • machine-controller-managerTurns Machine/MachineDeployment objects into real VMs.
  • etcd-druidThe etcd operator: deploys members and the backup-restore sidecar.
  • gardener-resource-managerApplies ManagedResource bundles and reverts drift; issues short-lived tokens.
  • dependency-watchdogTwo loops: a "weeder" restarts pods stuck after a dependency recovers; a "prober" scales controllers down when the shoot's API endpoint is unreachable, so nodes are not wrongly replaced.
  • vpn-seed-serverTerminates the reversed VPN the shoot dials out to.

Forks & odd names

  • PlutonoA fork of Grafana 7.5.17, kept at the last Apache-2.0 release after Grafana relicensed to AGPLv3 in 2021.
  • Vali / ValitailForks of Loki and Promtail, same licensing reason. Maintained by credativ.
  • LakomAn admission controller that rejects container images without a valid cosign signature.
  • Garden LinuxA Debian-derived, hardened node OS built for Gardener workers. Its own project, its own org, also under NeoNephos.

Gotchas

Ordered with the security consequences first, because those are the ones that are structural rather than fixable.

  1. A seed administrator can read every shoot's secrets and etcd on that seed. This is the central tradeoff of kubeception, not a defect. Isolation between two customers' control planes on a shared seed is ordinary Kubernetes namespace isolation — RBAC, NetworkPolicy, admission — with no hypervisor or cryptographic barrier. Operators who need a harder boundary solve it by not sharing the seed (seedSelector, dedicated seeds per tenant tier), because Gardener offers no in-seed sandbox for control planes. If you evaluate Gardener as a consumer, "who operates the seed" is the security question.
  2. Two CVSS 9.9 advisories in 2025 turned a Project admin into a seed compromise. CVE-2025-47283 and CVE-2025-47284, both published 19 May 2025, allowed a user with admin rights on a Gardener Project — a role most operators think of as an ordinary tenant — to escalate to control of the seed clusters hosting their shoots. Fixed in v1.116.4 / v1.117.5 / v1.118.2 / v1.119.0. Separately, CVE-2025-67508 (CVSS 8.0) let a project admin plant credential values that executed as commands on an operator's own machine in non-POSIX shells — fixed in gardenctl v2.12.0.
  3. The plugin that scopes a gardenlet to its own seed does not deny anything today. SeedAuthorizer is Gardener's analogue of Kubernetes' Node authorizer: it walks a dependency graph to check that a requested object actually belongs to the seed asking for it. But the documentation is explicit that, for backwards compatibility, it never returns a deny decision — a request that fails the graph check simply falls through to the next authorizer, normally RBAC. It widens access on a match rather than narrowing it on a miss. Read your RBAC accordingly; the graph is not the boundary you might assume. Its write-side companion is a different animal: SeedRestriction is an admission plugin — Gardener's version of Kubernetes' NodeRestriction — which limits which objects a gardenlet may modify, and an admission plugin does reject.
  4. Almost every security feature is opt-in, and the PodSecurity default is privileged. A shoot created with no extensions enabled has default-deny NetworkPolicy scaffolding — and that is about it. Image-signature enforcement (Lakom), runtime detection (Falco), syscall sandboxing (gVisor) and egress filtering are all separate extensions a landscape operator must install. If no PodSecurity label is set, admission enforces privileged.
  5. SecretBinding is a wall, not a deprecation warning. Shoots running Kubernetes 1.34 or newer cannot use it at all — only CredentialsBinding is accepted. Anyone whose mental model or Terraform module still says "SecretBinding attaches cloud credentials" hits a hard failure on the next minor upgrade rather than a warning.
  6. Version expiry force-upgrades you, and opting out of auto-update does not stop it. Once a Kubernetes or machine-image version is past its expirationDate in the CloudProfile, the next maintenance window upgrades that cluster regardless of the owner's auto-update preference. This is the intended behaviour and it is what makes fleet-wide EOL management work — but teams who disabled auto-update believing they had frozen their version are wrong, and find out on a Tuesday night.
  7. Hibernation stops compute, not billing. Persistent volumes, LoadBalancer services and floating IPs keep their addresses and keep charging while a cluster is hibernated. Expect a real saving on nodes, not a zero.
  8. Infrastructure reconciliation still defaults to Terraform, and moving off it is one-way. Despite the pods-and-controllers aesthetic, the AWS extension's default Infrastructure reconciler runs Terraform in a job in the seed. The native Go SDK path — the "flow" reconciler — is opt-in per shoot via the annotation aws.provider.extensions.gardener.cloud/use-flow="true", and its own documentation states plainly that the migration is not revertible.
  9. There is no point-in-time recovery. etcd backup is a full snapshot daily plus deltas every five minutes or 100 MiB. Restoration is from the latest snapshot, full stop — an incident loses whatever landed in the gap. Restoring the garden cluster itself is worse: an ordered manual procedure where getting the encryption-key restore wrong renders data inaccessible or destroys it.
  10. Version skew is a landscape-wide constraint, not a per-cluster one. A gardenlet may run up to two minor versions behind the gardener-apiserver, but extensions must build against a library version no newer than the oldest gardenlet in the landscape. One straggler seed therefore pins extension versions everywhere. And gardener-operator refuses to start — it crashes — if an upgrade skips a minor version or is downgraded.
  11. Ceilings arrive earlier than the Kubernetes documentation implies. Gardener's own scalability guidance: etcd should stay under 8 GB with fewer than 100k objects, a kube-apiserver pod under 3 cores and 16 GB, and a shoot practically under 500 nodes — against Kubernetes' nominal 5,000-node limit. Plan the fleet as many medium clusters, which is the shape Gardener is built for anyway. If any of this feels abstract, Section 10 puts a real landscape on your laptop in about half an hour.
10

Run it yourself

Being honest up front: there is no zero-install path. No hosted demo, no playground, no sandbox. Gardener needs a Kubernetes cluster before it can give you Kubernetes clusters, and that is true on your laptop too. What follows is real: the project's own kind-based landscape, which runs a full garden, a seed and a shoot on one machine.

Everything below was read from the gardener/gardener repository at v1.148.x. You need Docker, Go, make, git, jq, kubectl and yq installed. The last two matter and are easy to skip: the Makefile does download its own pinned copies of kind, helm, skaffold, kubectl and yq, but it only puts them on PATH for the lifetime of a make process — and you will be typing kubectl yourself, and the helper scripts call kubectl and yq directly. The documented floor is 8 CPU, 16 GiB memory and 120 GiB disk — set that in Docker Desktop's resource settings before you start, or the seed will never go ready. Apple Silicon is fine: hack/tools.mk maps uname -m to arm64 and fetches native binaries.

LAB A — A real shoot cluster on your laptop

~20–30 min · Docker + Go + 16 GiB

This uses a workerless shoot — a control plane with no worker nodes — which is a real Gardener feature and skips the slowest, most memory-hungry part. You still see the whole garden → seed → shoot chain.

  1. Clone the repository. The local setup lives in the main repo; there is nothing else to install.

    git clone --depth 1 https://github.com/gardener/gardener
cd gardener

    EXPECT: a Makefile, a dev-setup/ directory and an example/provider-local/ directory.

  2. Create the kind cluster that will be both garden and seed. Expect a sudo prompt: this step edits two files on your machine. It appends registry.local.gardener.cloud to /etc/hosts (both 127.0.0.1 and ::1, for the local image registry), and on macOS it writes /etc/resolver/local.gardener.cloud so the rest of the landscape's hostnames resolve through the cluster's own DNS. Neither is something you edit by hand.

    make kind-up
export KUBECONFIG=$PWD/dev-setup/kubeconfigs/runtime/kubeconfig

    EXPECT: a kind cluster named gardener-local, ready in 1–3 minutes. Verify with kubectl get nodes.

  3. Deploy Gardener itself. This is the slow step — Skaffold compiles roughly two dozen Go binaries locally and Helm-installs them. Budget 10–20 minutes on a cold Go build cache; later runs are far quicker.

    make gardener-up

    EXPECT: Skaffold build output, then pods coming up in the garden namespace — gardener-apiserver, gardener-controller-manager, gardenlet, etcd-druid and the rest of Section 8's inventory.

  4. Wait for the seed to report ready. From here on you talk to the virtual garden — the API server Gardener runs for its own objects — not the kind cluster's API.

    export KUBECONFIG=$PWD/dev-setup/kubeconfigs/virtual-garden/kubeconfig
./hack/usage/wait-for.sh seed local \
    GardenletReady SeedSystemComponentsHealthy ExtensionsReady

    EXPECT: the script returns cleanly. kubectl get seed local shows STATUS: Ready.

  5. Order a cluster. One apply. This is the object from the SHOOT tab in Section 4, in its local-provider form.

    kubectl apply -f example/provider-local/shoot-workerless.yaml

NAMESPACE=garden-local ./hack/usage/wait-for.sh shoot local-wl \
    APIServerAvailable ControlPlaneHealthy \
    ObservabilityComponentsHealthy SystemComponentsHealthy

    EXPECT: kubectl -n garden-local get shoot local-wl climbs through LAST OPERATION percentages — those description strings are the flow task names from Section 4's RECONCILE tab, live.

  6. Look at the trick directly. Switch back to the seed's kubeconfig and list the pods in the shoot's control-plane namespace. This single command is the entire point of this sheet.

    export KUBECONFIG=$PWD/dev-setup/kubeconfigs/runtime/kubeconfig
kubectl -n shoot--local--local-wl get pods

    EXPECT: etcd-main-0, etcd-events-0, kube-apiserver-…, kube-controller-manager-… and friends — a Kubernetes control plane, running as ordinary pods, in a namespace, on someone else's cluster. Compare with FIG. 3-1.

  7. Tear it all down when you are finished. This removes the kind cluster and everything in it.

    make kind-down

    EXPECT: docker ps shows no gardener-local containers.

LAB B — Real worker nodes, and a kubeconfig you can use

+20 min · continues from LAB A

Same landscape, but now with a shoot that has worker nodes. The local provider's machine-controller-manager creates each "VM" as a Docker container running a kind node image — so you get the real code path with none of the cloud bill.

  1. Create the full shoot. Its worker pool asks for one to two nodes of machine.type: local.

    export KUBECONFIG=$PWD/dev-setup/kubeconfigs/virtual-garden/kubeconfig
kubectl apply -f example/provider-local/shoot.yaml

NAMESPACE=garden-local ./hack/usage/wait-for.sh shoot local \
    APIServerAvailable ControlPlaneHealthy ObservabilityComponentsHealthy \
    EveryNodeReady SystemComponentsHealthy

    EXPECT: kubectl -n garden-local get shoot local eventually reads STATUS: healthy, and docker ps shows new node containers appearing.

  2. Request a kubeconfig — the short-lived, subresource-based kind from Section 4. The helper script wraps the raw API call shown there.

    ./hack/usage/generate-kubeconfig.sh > admin-kubeconf.yaml
kubectl --kubeconfig admin-kubeconf.yaml get nodes

    EXPECT: your worker nodes listed as Ready. If this hangs, disable any VPN on your host — the local landscape's networking does not survive one.

  3. Prove the split. Ask the shoot for its control-plane pods; there are none. Then ask the seed; they are all there.

    kubectl --kubeconfig admin-kubeconf.yaml -n kube-system get pods
# → coredns, kube-proxy, calico, vpn-shoot … and NO apiserver, NO etcd

export KUBECONFIG=$PWD/dev-setup/kubeconfigs/runtime/kubeconfig
kubectl -n shoot--local--local get pods
# → the control plane, in full

    EXPECT: two disjoint lists. That is the whole architecture in two commands.

  4. Hibernate it, then wake it. Watch the control-plane pods disappear from the seed and the node containers vanish from Docker — then come back with etcd's contents intact.

    export KUBECONFIG=$PWD/dev-setup/kubeconfigs/virtual-garden/kubeconfig
kubectl -n garden-local patch shoot local --type=merge \
  -p '{"spec":{"hibernation":{"enabled":true}}}'

    EXPECT: the shoot reports Hibernated; the seed namespace empties out. Flip enabled back to false and everything returns.

  5. Delete the shoot. Note the confirmation annotation — Gardener rejects an unconfirmed delete on purpose.

    ./hack/usage/delete shoot local garden-local

    EXPECT: the script annotates confirmation.gardener.cloud/deletion=true and then deletes. Without that annotation, the API server refuses the request.

LAB C — Graduate: the tools operators actually use

optional · ~15 min each

  1. Target your landscape with gardenctl. The official CLI, built as a set of kubectl plugins. Its real value is moving between gardens, seeds and shoots without juggling kubeconfigs.

    brew install gardener/tap/gardenctl-v2

export KUBECONFIG=$PWD/dev-setup/kubeconfigs/virtual-garden/kubeconfig
identity=$(kubectl -n kube-system get configmap cluster-identity \
             -o jsonpath='{.data.cluster-identity}')
gardenctl config set-garden "$identity" --kubeconfig "$KUBECONFIG"
source <(gardenctl rc bash)     # or zsh / fish / powershell
gardenctl target --garden "$identity"

# gardenctl has no 'get' — listing is still plain kubectl,
# against the virtual-garden kubeconfig you exported above:
kubectl get shoots -n garden-local

    EXPECT: gardenctl target confirms the garden, and kubectl lists your shoots. Two honest limits: gardenctl's whole surface is ssh, sshpatch, target, config, provider-env, kubectl-env, kubeconfig, resolve, rc and version — it moves you between clusters rather than replacing kubectl. And gardenctl target --shoot normally hands you credentials through the gardenlogin auth plugin, which this local setup does not configure, so keep using generate-kubeconfig.sh from LAB B. Use v2.12.0 or newer: earlier versions carry CVE-2025-67508.

  2. Run the Gardener Dashboard against your landscape. This is what end users see, and there is no public demo of it — running it locally is the only way to try it.

    git clone https://github.com/gardener/dashboard && cd dashboard
yarn

# REQUIRED before starting the backend — it asserts on these three
# keys at boot and crashes without them. Write ~/.gardener/config.yaml:
cat > ~/.gardener/config.yaml <<'YAML'
port: 3030
apiServerUrl: https://api.virtual-garden.local.gardener.cloud
sessionSecret: c2VjcmV0
websocketAllowedOrigins:
- https://localhost:8443
YAML

# backend, in one terminal:
cd backend && export KUBECONFIG=<path-to>/virtual-garden/kubeconfig && yarn serve
# frontend, in another:
cd frontend && yarn setup && yarn serve

    EXPECT: https://localhost:8443/. Skip the config file and yarn serve dies immediately on an assertion for sessionSecret, apiServerUrl and websocketAllowedOrigins — that is the one step people miss. Confirm apiServerUrl against your own landscape with kubectl config view --minify -o jsonpath='{.clusters[].cluster.server}'. Then log in with a token: kubectl -n garden create serviceaccount dashboard-user, bind it to cluster-admin, and kubectl -n garden create token dashboard-user --duration 24h.

  3. Read one extension end to end. The fastest way to understand the contract in Section 5 is to read the reference implementation — provider-local, which satisfies the whole contract against kind and is the thing you have been running all along.

    ls pkg/provider-local/controller/
# infrastructure/ worker/ controlplane/ dnsrecord/ ...
# one directory per resource kind from FIG. 5-1

    EXPECT: a directory per extension resource kind, each implementing the same Actuator interface — Reconcile, Delete, Migrate, Restore, ForceDelete. That interface is the whole extension API.

  4. Only then, consider a real cloud. Be clear-eyed about cost: a landscape on a hyperscaler means a garden cluster, a seed cluster and each shoot's workers — comfortably past any free tier within hours. If you go there, use time-boxed trial credit and set a billing alarm before the first apply.

    EXPECT: no free lunch. This is the rung where Gardener stops being a laptop exercise and starts being a platform-team commitment.

Glossary — the jargon, decoded

Garden cluster
The always-on Kubernetes cluster that runs Gardener itself — its API server and controllers — and holds every Shoot, Seed, Project and CloudProfile object. One per landscape.
Seed cluster
An ordinary, conformant Kubernetes cluster whose job is to host other clusters' control planes as pods. Gardener does not create it; it only requires that one exists and runs a gardenlet. Roughly one per provider per region.
Shoot cluster
The cluster an end user receives, and the API object that orders it. Physically it is only worker nodes — its control plane lives in a seed. architecture docs
Kubeception
The name for running clusters' control planes inside another cluster. Gardener's own README calls the architecture "kubeception or inception design," after the film. Also known generically as hosted control planes.
Landscape
One complete Gardener installation: a garden cluster, its seeds, and every shoot beneath them. Used constantly in the documentation; it is not an API type.
gardenlet
The agent running in every seed, deliberately modelled on the kubelet. It reconciles only the shoots assigned to its own seed, and it initiates the connection to the garden cluster rather than receiving one. concept doc
Aggregated API server
A standard Kubernetes extension point: a second API server registered behind the main one via an APIService, so its types get real API-machinery behaviour — admission, validation, subresources, watch — rather than CRD semantics. Kubernetes docs
Project
Gardener's tenancy unit. Each Project owns a garden-<name> namespace in the garden cluster, and shoots, credentials and RBAC are scoped inside it.
CloudProfile
The catalogue, per infrastructure, of what shoots are allowed to ask for: machine types, machine images, regions, and Kubernetes versions — each version carrying a classification and an expiry date. It is what makes fleet-wide version policy enforceable.
CredentialsBinding
The object that links a shoot to its infrastructure credentials, referencing either a Secret or a WorkloadIdentity. It replaced SecretBinding, which is rejected for shoots on Kubernetes 1.34 and newer.
WorkloadIdentity
Gardener issuing short-lived OIDC tokens that a cloud provider federates against, so a shoot can authenticate to AWS, Azure or GCP with no static credential stored anywhere.
ManagedSeed
A shoot promoted to also act as a seed — informally "a shooted seed." The parent gardenlet clones itself into it. This is how most production fleets grow their seed capacity.
etcd (main and events)
Every shoot gets two etcd instances: etcd-main for cluster state, and etcd-events for high-churn Event objects. Only etcd-main is backed up — events are not worth the space or the restore time.
etcd-druid
The operator that runs those etcd instances: members, the backup-restore sidecar, snapshot scheduling and defragmentation. Deliberately ships no liveness probe, on the reasoning that restarting an unhealthy etcd usually makes things worse. github.com/gardener/etcd-druid
machine-controller-manager
Creates and destroys worker VMs from Machine, MachineSet and MachineDeployment objects that mirror Pod, ReplicaSet and Deployment. Predates Cluster API and influenced its machine model. repository
OperatingSystemConfig
Gardener's OS-neutral description of what a worker node must have — files and systemd units. An OS extension translates it into that distribution's real bootstrap format, and gardener-node-agent applies it on the node.
gardener-node-agent
A systemd service, not a pod, on every worker node. It watches its OperatingSystemConfig and restarts only the units that actually changed — replacing an older polling shell script.
Reversed VPN
The tunnel that lets a shoot's API server reach pods and nodes. The shoot dials out to the seed, so the shoot's network needs no inbound rule and no load balancer of its own. The original design ran the other way and cost roughly €20/month per cluster.
SNI passthrough
How one load balancer per seed serves every shoot's API server: an Istio gateway reads the requested hostname from the unencrypted part of the TLS handshake and forwards the still-encrypted stream to the right namespace. Without it, each shoot would need its own load balancer.
Flow
Gardener's internal execution engine: a directed acyclic graph of named tasks run with maximum parallelism. Creating a shoot is 122 such tasks, and their names are the strings you see in a Shoot's status.lastOperation.description.
Hibernation
Scaling a shoot's workers and control plane to zero, on demand or on a cron schedule. etcd's contents and persistent volumes survive; the compute does not, and neither does the bill for storage and load balancers.
Bastion
A short-lived VM Gardener provisions on request to allow SSH to worker nodes, with firewall rules scoped to your source address and a hard lifetime cap. There is no other SSH path into a shoot's nodes.
GEP
Gardener Enhancement Proposal — the project's design-document process, equivalent to a Kubernetes KEP. GEP-1 is the split that moved provider code out of the core. github.com/gardener/enhancements
